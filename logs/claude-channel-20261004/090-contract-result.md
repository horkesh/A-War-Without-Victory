## 1. Authored duration and constructor (absent field vs explicit false)
- `SOUTHERN_MOVE_95_OPPORTUNITY` (catalog 532-575) authors `planning_duration: 2`, `min_attack_outcome: 'repulsed'`, staging `op:sipovo:sipovo_2`, `staff_recommendation: 'approve'`. It has **no** `is_pre_planned`, `force_launch`, `preparation_*` or other launch-override field; `OperationOpportunityDef` (`operation_opportunities.ts` ~207-232) has none to set, and documents `planning_duration` only as "Planning duration once approved."
- Constructor (`spawnCorpsOperationFromOpportunity` ~1330-1346) calls `buildCorpsOperation({name, planning_duration: def.planning_duration, staging_osid, min_attack_outcome}, axes, participants, turn, **false** /* is_pre_planned: false — opportunity ops do NOT occupy slot 0 */, undefined)`. This is an **explicit authored false**, whose stated reason is slot ownership. `buildCorpsOperation` only writes `is_pre_planned: true` when the flag is true (`corps_operation_helpers.ts` ~337), so the stored op has the field **absent** (confirmed in 089's stored op); no `force_launch`/`preparation_*` is set at construction.

## 2. Generic initialization and consumers
- `tickPreparation` (`operation_preparation.ts` ~893-903) sets `preparation_max_turns = max(max(2, 8 - aggressiveness), planning_duration)` at the first tick; its comment: "If the op definition specifies planning_duration, preserve it as the full march/preparation budget before the anti-paralysis timeout can fire." So the authored value is a **floor** on the budget, never a cap.
- The bypass is keyed on `is_pre_planned === true` (~910): "Pre-planned ops bypass the preparation state machine — objectives, staging, and timing are author-validated." Opportunity ops are also author-validated (catalog citations, authored staging/objectives), but are excluded from that bypass by the **slot** flag, not by a preparation decision. Nothing found says whether that coupling is intended or incidental.
- Consumers of `preparation_max_turns`: `tickPreparation` (anti-paralysis ~941, sync wait ~1098), UI adapters, scenario trace. In the planning loop the prep gate precedes the readiness gates (089).

## 3. Authority text (canon read; precedence Invariants > Systems Manual > Rulebook)
- **Systems Manual** (lines ~407-421): "`planning_duration` march/preparation budget: `preparation_max_turns` is initialised as `max(getPreparationMaxTurns(aggressiveness), op.planning_duration ?? 0)` so authored routes retain their full deterministic assembly and anti-paralysis window. The value is not a mandatory staff delay after readiness ... If readiness never arrives, budget expiry opens the existing forced-attempt or named-recovery path". It also states the anti-paralysis valve, the intel/probe mechanic and that "unresolved probes block preparation advancement".
- **Engine Invariants** (473): "`planning_duration` is the deterministic march/preparation and anti-paralysis budget: it bounds how long the operation may wait for assembly, and expiry opens the existing forced-attempt or named-recovery path." Rulebook (323): "the duration is the marching/preparation budget and anti-paralysis deadline, not a mandatory delay after readiness."
- **Tension (not a contradiction proven):** read literally, Invariants/Rulebook say the authored duration *is* the deadline; the Systems Manual and code make the effective deadline `max(aggressiveness-derived, authored)`, so authored 2 yields 5. Higher precedence is Invariants, but it does not say "exactly" or "only", and the Systems Manual states the max rule as the current mechanism. Minor doc drift: the Manual writes `getPreparationMaxTurns(comp, agg)` (two arguments); the code takes aggressiveness only. Whether the Invariants wording should be tightened or the max rule is the intended reading is a **canon question**, not decided here.
- **Tests (text only, not run):** `tests/operation_opportunities_substrate.test.ts:402` asserts `op.is_pre_planned` is undefined for opportunity ops ("never occupy slot 0"): contract evidence for the **slot** meaning only. `tests/commander/anti_paralysis_supply_gate.test.ts` covers the timeout supply gate (fixture `preparation_max_turns: 5`); `tests/sector_offensive_launch_gates.test.ts` fixtures use `preparation_max_turns: 5`. I found **no** test asserting that opportunity ops follow, bypass or shorten the preparation machine.

## 4. date_window / expires_turn (does it bound an ACTIVE op?)
- `dateWindowSouthernMove` (catalog 447-451) is an axis predicate evaluated during opportunity evaluation: it gates **admission** (`turn < 182` and `turn > 188` red). Outside the opportunity module and catalogs, `date_window` appears only in the axis-name lists/validator (`operation_opportunities.ts`, `validateGameState.ts`); no consumer reads it for an already-spawned `CorpsOperation`, and `sector_offensive.ts` has none.
- `expires_turn` = `defaultExpiryTurn(turn) = turn + 24` (n39 stored 209 = 185 + 24; "the catalog can always store the actual window inside the evaluator closure"), not the date window. Its direct consumer (~787) marks only proposals in `eligible_pending_review`/`delayed` as `expired`; approved/spawned ops are not touched. So neither the date window nor `expires_turn` bounds active-operation execution. A 188 capture target is a historical/owner target, not a production deadline.
