## 1. Order-time predictor (exact source, not comments)
- Call: `bot_brigade_eval_attack.ts` ~365: `predictCombatOutcome(state, brigade.id, currentObjective, adjacency, reverseMap, terrainCache, 'attack', undefined /*additionalAttackers*/, supplyStateByOsid, osidPopulationMap, undefined, ethnicMap, prefix, officerLookup)`: one attacker, posture override `'attack'`, no additional attackers. The result's `power_ratio` is the order record's `power_ratio` (1.296 at t188); concentration is handled separately by `estimateConcentratedOutcome(prediction.power_ratio, additionalAttackers)` (~400).
- Defender scope (`combat_predictor.ts` ~254-420): requires the attacker active and the target tactically adjacent; if the target is enemy-controlled it finds the defending sector (`findSectorForEnemyOsid`), takes `getStandingOgDefenseBrigadeIds(sector)` filtered `status active && isStandingOgDefenseBrigadeAvailable`, **adds the physical defenders at the target** (`collectDefenderFormationsAtTarget`), sorts by id, ranks (`rankDefendersByPowerWithEntries`), and sums per-brigade power: brigades **at the target OSID** at full power (`physicalPower`), others as **reserves** weighted by `getReactiveDistanceWeight(bfsDistanceFriendly(...))` and a home-municipality bonus; `reactiveResponse = min(boostedReserves, attackerCount * avgReactivePower * REACTIVE_DEFENSE_RATIO)` with `attackerCount = 1 + additionalAttackers` (= 1 here) and the sector-stance bonus; `applyMinimumSectorDefenseFloor`; militia floor only if no physical defender. Then **`defenderPower = defenderFloor * fogMult`**, `fogMult = FOG_BASE (0.70) + FOG_INTEL_SCALE (0.25) * getSectorPairIntelConfidence(state, attackerLoc, sector_id)`, raised to at least `FOG_AFTER_RETREAT_CAP (0.95)` if the attacker retreated/was repulsed from the target within 3 turns. Then enclave garrison power, seasonal defence mult, `powerRatio = attackerPower / defenderPower`, `classifyOutcome`, and a morale downgrade (`costly_victory` -> `stalemate` when the defender's morale >= a floor).
- Attacker side: `sum(computeAttackerPower(.., posture 'attack', ..) * getBrigadeExecutionAttackPowerMult) * coordPenalty * seasonal.attack_mult`.

## 2. Resolver (same blob at clean; `attack_resolution_osid.ts`)
- Defender scope (~758-880): the same sector roster (`getStandingOgDefenseBrigadeIds` + `isStandingOgDefenseBrigadeAvailable`) **plus physical defenders**, sorted, `rankDefendersByPower`, per-brigade `computeDefenderPower`, physical at full power / reserves by `getReactiveDistanceWeight(bfs hops)` and home bonus, stance bonus, `reactiveResponse = min(boostedReserves, attackerFormations.length * avgReactivePower * REACTIVE_DEFENSE_RATIO)`, minimum sector floor, militia floor if no physical defender, enclave garrison (~944). Casualties are then distributed by the same per-brigade weights, which is why several defender brigades carry the battle id (094).
- Resolver-only on the defender side: (a) **anchor-garrison filter** (~773-795) dropping sector brigades that stand on their corps's must-hold OSID unless within `ANCHOR_GARRISON_LOAN_MAX_HOPS` of the target; (b) `boostedReserves = effectiveReserves * stanceBonus / simultaneousAxes` (~850); (c) `findEmptySectorAdjacentDefenders` fallback if the roster is empty; (d) `getCollapseDefenderMultiplier`, `getPostWashingtonJointPressureMultiplier`, **last-stand x1.5** when the defender has no retreat destination (~960-985), and `intelFriction.defenderPowerMult` (~1085). No fog discount.
- Resolver-only on the attacker side (~1017-1058, ~1083): the attacker's **actual posture** (`POSTURE_ATTACK`, falling back to 'attack'), `SUPPORT_POWER_MULT` for support brigades, **`getConcentrationBonus`** (op-mates within 2 hops via `countAxisConcentrationSupport`), **`tempoMult` = `getWarExhaustionTempoMult`**, `firepowerDeficitMult`, TG donor power (flag-gated), and `intelFriction.attackerPowerMult` (so `effectiveAttackerPower = attackerPower * intelFriction.attackerPowerMult`). `powerRatio = effectiveAttackerPower / defenderPower` -> `classifyOutcome`.

## 3. Side-by-side verdict on the candidate
- **Shared (same helpers, same rule):** sector roster + physical-defender union and sort; per-brigade power and rank helpers; physical-vs-reserve split with `getReactiveDistanceWeight` and home bonus; stance bonus; reactive cap form (with 1 attacker here: both use 1); minimum floor; enclave garrison; `classifyOutcome`. **Cardinality is not different by design**: multi-defender in both. The weekly row's single `defender_brigade` is the `primary` of that ranked set, not the set.
- **Intended-by-comment difference:** the predictor docstring states "Uses the same formulas as attack_resolution_osid.ts but with FOG OF WAR: defender power is discounted because commanders don't know exact enemy strength" (`combat_predictor.ts` ~244-249). So the fog factor (0.70-0.95 of true defender power) is an intentional estimate-vs-truth difference, not an omission.
- **Other bound differences (direction not computed, magnitudes unreported):** resolver anchor-garrison filter and `simultaneousAxes` split (both can only shrink the resolver's defender relative to the predictor's); resolver last-stand, collapse and post-Washington multipliers; resolver-only attacker terms `tempoMult`, `firepowerDeficitMult`, `intelFriction`, support/concentration multipliers and the real posture. I did not read the values or sign conventions of these multipliers.
- **Arithmetic only (not a cause):** if attacker terms and defender sets were identical and the only difference were the predictor's fog, then `fogMult = 0.93 / 1.296 = 0.718` (with 0.93 rounded, `[0.925, 0.935) / 1.296 = 0.714-0.721`), i.e. a sector-pair confidence of about `(0.718 - 0.70)/0.25 = 0.07` (0.055-0.086). That lies inside the allowed fog range [0.70, 0.95], so fog **can** account for the whole gap in principle; the resolver-only attacker modifiers can too; neither is shown to. The sector-pair confidence and the multiplier values at t188 are unreported.
- Therefore the single-predictor-vs-multi-resolver candidate is **rejected as a source possibility**; the stored 1.296 vs 0.93 remains **unclassified** (fog, resolver-only modifiers, or anything else), not a defect and not shown to be ordinary variance.
