## Deliverables

### Phase A: Assignment Only — No Combat Change (~1 session)
**Assigned to:** Gameplay Programmer

Data preparation. Brigades get sub-segment assignments. No combat formula changes. No regression possible.

- [ ] **A1.** Extend `SubSegment` type in `src/sim/combat/corps_front_sectors.ts` — add `primary_brigade_ids: string[]` field (~5 lines)
- [ ] **A2.** Add `assigned_sub_segment_id?: string` to `FormationState` in `src/state/game_state.ts` (~3 lines)
- [ ] **A3.** Implement `assignBrigadesToSubSegments()` in `src/sim/combat/corps_front_sectors.ts` — home-proximity affinity algorithm per design doc: separate front/reserve, compute affinity (hop distance + home bonus + mech terrain bonus), greedy best-fit widest-first. Constants: `WIDE_SEGMENT_THRESHOLD=5`, `HOME_AFFINITY_BONUS=1.3`, `MECH_TERRAIN_BONUS=1.2` (~80 lines)
- [ ] **A4.** Wire `assignBrigadesToSubSegments()` into war phase pipeline (`src/sim/turn_phases/war_phases.ts`) — call after sector construction, before combat resolution (~10 lines)
- [ ] **A5.** Write tests in `tests/brigade_aor_subsegment.test.ts` — assignment correctness: home affinity wins, wide segments get 2+ brigades, every front-line brigade assigned, every sub-segment covered if possible (~80 lines)
- [ ] **A6.** Verify assignments appear in save file (`data/derived/latest_run_final_save.json`) — run 40w, inspect sub-segment primary_brigade_ids populated

**Gate:** All tests pass. `tsc --noEmit` clean. 40w scenario runs without error. Save file shows assignments. No calibration change (combat unchanged).

**Architect decision (flag for user):** Should `assignBrigadesToSubSegments` run every turn or only when sector composition changes? Design doc implies every turn. Recommend: every turn with hysteresis (skip reassignment if current assignment affinity is within 80% of best — prevents entrenchment-destroying churn in Phase D).

### Phase B: Combat Integration (~1 session)
**Assigned to:** Gameplay Programmer

The calibration-sensitive phase. Defense becomes non-uniform.

- [ ] **B1.** Add `findSubSegmentForOsid(sector, targetOsid)` utility in `src/sim/combat/corps_front_sectors.ts` — returns the sub-segment containing the attacked OSID (~15 lines)
- [ ] **B2.** Modify `computeDefenderPower` in `src/sim/combat/sector_defense.ts` — primary brigade power / sub-segment edges + reactive from neighbors via existing Layer A. Fallback to current uniform formula if sub-segment has no primary brigade (gap case handled in Phase D) (~50 lines changed)
- [ ] **B3.** Update `combat_predictor.ts` to match — bot prediction must use same per-sub-segment defense formula (~30 lines)
- [ ] **B4.** Write tests: defense at strong sub-segment > old uniform, defense at weak sub-segment < old uniform, reactive contribution verified, gap (no primary) uses reactive-only (~60 lines)
- [ ] **B5.** Run 40w calibration. Record area-weighted %. Compare to current baseline (n786: 90.5%). If deviation >2pp, adjust reactive decay constant.
- [ ] **B6.** Run full vitest suite — verify no combat test regressions

**Gate:** 40w within 2pp of baseline. All tests pass. `tsc --noEmit` clean.

**Architect decision (flag for user):** If calibration deviates >2pp, the reactive decay constant (0.60) is the primary tuning lever. Increasing it (e.g. 0.70) strengthens mutual support, reducing texture. Decreasing it sharpens texture. Architect proposes adjustment; user approves.

## Cross-Plan Integration Note

**v0.4.1 Event Bus:** Front line gap creation ("Sub-segment uncovered — 213th Vitežka has fallen back") and breakthrough events should eventually post through the v0.4.1 universal event bus. For v0.3.3, gap detection produces **data only** (`gap: boolean` on SubSegment). Event emission is deferred to v0.4.1 integration. No parallel notification system.

**v0.3.2 dependency:** v0.3.2 (humanitarian fix) should land first to establish correct capital baseline. v0.3.3 is independent of humanitarian capital but benefits from a stable calibration baseline. Can execute in parallel if needed.

**Negotiation capital:** Front line stability (gap frequency) should feed `military_position` capital in `compute_capital.ts`. Deferred to v0.4.1+ per cross-plan review Finding 2. Not in v0.3.3 scope.
