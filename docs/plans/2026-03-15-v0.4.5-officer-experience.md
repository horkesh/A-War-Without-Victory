## Situation

Named officers exist with static ratings (competence, aggressiveness, defensive_skill) but **never improve.** The types already have `can_improve: boolean` and `improvement_rate: number` on every officer — the system was designed for growth but never hooked up to outcomes.

**What exists:**
| Feature | Status |
|---------|--------|
| Named officers with ratings (1-5) | LIVE — 84 officers, 3 factions |
| `can_improve` + `improvement_rate` on NamedOfficer | LIVE — fields set per officer, never read |
| Operation AAR with commander tracking | LIVE — op outcomes + commander_officer_id |
| Officer succession (player-choice) | LIVE — replacement_suggested events |
| War crimes records (informational) | LIVE — 29 officers annotated |
| `political_reliability` rating | LIVE — never mechanically used |
| `available_until_turn` (departure) | LIVE — RS brain drain via scripted departures |
| Brigade `officer_quality` abstraction | LIVE — 0-1 scale, `getBrigadeOfficerMod()` |

**What's missing:**
- Post-operation experience gain (competence growth)
- Aggressiveness/defense skill shift from what the officer actually does
- ARBiH learning curve (faster improvement)
- Warlord friction mechanic (independent commanders ignore orders)
- Commander relationship events
- Experience UI (progression display)

---

## Design Principles

1. **Organic emergence, not scripted arcs.** The ARBiH transformation from militia to professional army should emerge from officers gaining experience through combat — not from a hard-coded switch at week X.

2. **The RS trap.** VRS officers start excellent (JNA-trained, competence 4-5) but depart via `available_until_turn`. Replacements are worse. The player watches institutional knowledge drain away. This is already modeled — v0.4.5 makes it felt.

3. **Personality matters.** An aggressive commander who runs 5 successful offensives becomes MORE aggressive. A defensive commander who holds a siege becomes a fortress specialist. Officers develop character through action.

4. **Friction is historical.** Dudaković launched operations without Sarajevo's approval. Orić ran Srebrenica as a personal fiefdom. These weren't bugs — they were features of a decentralized command structure. The player manages personalities, not automata.

### Phase 1: Post-Operation Experience Gain (~1 session)
**Assigned to:** Gameplay Programmer

Hook officer experience into the operation AAR system that already tracks outcomes.

- [ ] **`src/sim/combat/officer_experience.ts`** — NEW. Core experience engine:
  - `applyOperationExperience(state, operationAAR)`: called after operation completes
  - Competence gain formula:
    ```
    base_gain = improvement_rate × EXPERIENCE_BASE (0.1)
    outcome_mult = decisive_victory: 1.5, victory: 1.2, costly: 1.0, stalemate: 0.5, repulsed: 0.3, catastrophic: 0.1
    competence += base_gain × outcome_mult
    ```
  - Competence capped at 5 (maximum rating)
  - Only officers with `can_improve: true` gain experience (most ARBiH, few RS)
- [ ] **Skill shift** — aggressiveness and defensive_skill drift toward what the officer does:
  - Commanded offensive operation: `aggressiveness += 0.05`, `defensive_skill -= 0.02`
  - Commanded defensive hold (sector stance Fortify/Defend for 10+ turns): `defensive_skill += 0.05`, `aggressiveness -= 0.02`
  - Shift capped at ±1 from starting value (officer personality bends but doesn't break)
- [ ] **Store on NamedOfficerState** — add `experience_points: number` (cumulative), `operations_commanded: number`, `last_experience_turn: number`
- [ ] **Pipeline integration** — call `applyOperationExperience()` from `operation_aar.ts` when operation finalizes
- [ ] **Tests** — experience gain per outcome, competence cap, skill shift, can_improve guard

**Gate:** Officers gain competence from successful operations. ARBiH officers visibly improve over 52w run.

### Phase 3: Warlord Friction (~1 session)
**Assigned to:** Gameplay Programmer + Game Designer

Independent-minded commanders occasionally ignore army directives. This is historical — Dudaković, Orić, early ARBiH warlords operated semi-autonomously.

- [ ] **Friction probability** — each turn, for each corps commander with `political_reliability < 3`:
  ```
  friction_chance = (3 - political_reliability) × 0.05
  ```
  - Reliability 1: 10% chance per turn of ignoring directive
  - Reliability 2: 5% chance
  - Reliability 3+: 0% (loyal)
  - **DETERMINISM:** Use turn number + officer_id hash for pseudo-random (same input = same result). No Math.random().
- [ ] **Friction effects** — when friction triggers:
  - Commander ignores army stance directive (stays at previous stance instead of changing)
  - OR commander launches unauthorized operation (if aggressive + has target + no current op)
  - OR commander refuses to release brigades for army reserve (blocks elite loan)
- [ ] **Friction event** — `commander_friction` event shown to player:
  - "General Dudaković has launched an unauthorized offensive toward Bihać. 5th Corps is not following army directives this turn."
  - Player can: tolerate (lose political cohesion capital, commander stays), or relieve (lose competence, replace with lower-rated officer)
- [ ] **Faction differences:**
  - RBiH: highest friction (warlord culture, early war). Decreases as `faction_officer_maturity` rises.
  - RS: low friction (JNA discipline). Increases late war (demoralization, brain drain).
  - HRHB: moderate friction (Zagreb vs local commanders). Decreases post-Washington (Tuđman consolidates).
- [ ] **State** — `friction_events: Array<{ officer_id, turn, type, resolved }>` on MilitaryState
- [ ] **Tests** — friction probability, deterministic hash, event generation, player response effects

**Gate:** Warlord commanders occasionally disobey. Player sees friction events. Political cohesion affected.

### Phase 4: Commander Relationship Events (~0.5 session)
**Assigned to:** Gameplay Programmer

Personality-driven events beyond simple friction — commanders interacting with each other.

- [ ] **Event types** (5 scripted relationship patterns):
  - **Rivalry:** Two corps commanders in adjacent sectors refuse to coordinate operations. Effect: -10% combined power when both attacking same turn.
  - **Mentorship:** Senior officer (competence 4+) boosts junior (competence ≤ 2) in same faction. Effect: junior gains 2× experience for 10 turns.
  - **Insubordination escalation:** Officer with 3+ friction events in 20 turns threatens to resign. Player must promote (costs army cohesion) or accept resignation (lose experienced commander).
  - **Heroic stand:** Officer commanding a successful defense against 3:1 odds gains +1 aggressiveness and a morale boost for their corps (+5 corps-wide morale).
  - **Defeatism:** Officer commanding 3+ consecutive failed operations requests transfer. If denied, -0.3 competence penalty (demoralization).
- [ ] **Trigger conditions** — each event has specific trigger (e.g., rivalry triggers when two officers with aggressiveness ≥ 4 command adjacent corps)
- [ ] **Event UI** — reuse EventDecisionModal from v0.4.1. Commander events are a subtype of the event system.
- [ ] **Tests** — trigger conditions, event effects, determinism

**Gate:** Commander relationship events fire in a 52w run. Player responds. Effects visible.

## Determinism Handling

**Warlord friction uses deterministic pseudo-random:**
```typescript
function frictionCheck(officerId: string, turn: number, probability: number): boolean {
    // Hash officer ID + turn for deterministic "randomness"
    const hash = hashString(`${officerId}:${turn}:friction`);
    return (hash % 1000) / 1000 < probability;
}
```
Same officer + same turn = same friction result. Replay-safe.

## Calibration Impact

**Moderate — primarily affects long-run games (52w+):**
- ARBiH competence rise → slightly better combat performance late war (historically correct)
- RS brain drain → slightly worse late war (historically correct)
- Warlord friction → occasional efficiency loss for RBiH/HRHB (historically correct)
- Net effect: reinforces the designed faction arcs without changing early-war calibration

**Mitigation:** Experience gain rates are small (0.01-0.15 per operation). It takes 20+ operations to shift competence by 1 point. 40w calibration should be minimally affected.
