## Context

This milestone is fundamentally different from the others. Calibration is not "implement a feature" — it's "run the sim hundreds of times, find what's broken, fix it, verify, repeat." The last calibration ceiling was **89.0% area-weighted** at 40 weeks (n819).

This plan provides:
1. **Acceptance criteria** — what "calibrated" means, per faction, per scenario
2. **Calibration tooling** — automated benchmark suites, regression detection
3. **Calibration protocol** — the repeatable process for each scenario
4. **Known calibration debt** — issues from backlog that need resolution

It does NOT provide specific parameter changes — those emerge from the iterative process.

**Assigned to:** QA Engineer + Build Engineer

- [ ] **Task 1.1:** Create comprehensive benchmark runner
  - Create: `tools/run_benchmarks.ts`
  - Runs: 40w scenario (primary), 52w scenario, 208w scenario (if time allows)

  - Outputs: structured JSON report + human-readable summary
  - Pass/fail against acceptance criteria with color-coded output

- [ ] **Task 1.2:** Add per-faction quality check automation
  - Create: `tools/faction_quality_check.ts`
  - Reads final_save.json + weekly_report.jsonl
  - Checks each bullet in "Per-Faction Quality Checks" section
  - Binary pass/fail per check with diagnostic message on failure

- [ ] **Task 1.3:** Add regression detection
  - Create: `tools/calibration_regression.ts`
  - Compares current run metrics against stored baseline (from n819)
  - Flags any metric that regressed >2% from baseline
  - Stores baseline in `data/calibration/baseline_n819.json`

- [ ] **Task 1.4:** npm scripts
  - Add: `npm run calibrate:40w` — run 40w + benchmark + faction check
  - Add: `npm run calibrate:52w` — run 52w + benchmark + faction check
  - Add: `npm run calibrate:full` — run 208w + benchmark + faction check
  - Add: `npm run calibrate:regression` — run + compare against baseline

**Gate:** Automated benchmark suite runs all acceptance criteria. One command gives pass/fail.

### Phase 2: Scenario-Specific Calibration (~3-5 sessions, ITERATIVE)
**Assigned to:** Gameplay Programmer + War-or-Game

This phase is inherently iterative. The process per scenario:

1. Run `npm run calibrate:<scenario>`
2. Review failed metrics
3. Identify root cause (one change at a time — life lesson)
4. Apply fix
5. Re-run benchmark
6. /war-or-game sign-off
7. Record in CALIBRATION_MASTER.md

**Known calibration debt to address:**
- [ ] RS w20 benchmark (failed at -8.7% in n532, recovered but tight)
- [ ] Zero eligible attacker operations (58-106 per run — pre-screening gap)
- [ ] HRHB passivity structural analysis (settled, but verify with full event set)
- [ ] 2KK Prozor positional lock (partially addressed by commander override)
- [ ] Drina region OOB gap (partially fixed, 77-81%)
- [ ] Disconnected brigade assignment (1 remaining edge case)
- [ ] Late-war RS territorial decline (currently no mechanism to force decline)

**Events impact isolation (cross-plan finding #2):**
- [ ] Run benchmark with events DISABLED (skip evaluate_events step)
- [ ] Compare against events-enabled run
- [ ] Document net event impact on territory/casualties/IVP
- [ ] If impact >3% on any benchmark, tune event effect magnitudes before proceeding

**New calibration targets from v0.6.0 events:**
- [ ] Event effects don't cause cascade regressions (test: run with events ON vs OFF)
- [ ] Decision event outcomes don't create impossible game states
- [ ] Probabilistic events don't spike IVP/morale beyond reasonable bounds
- [ ] 208w full run reaches Dayton at w188 with plausible territory split

**Protocol per calibration attempt:**
```
1. ONE change only
2. npm run calibrate:40w (or :52w or :full)
3. Review benchmark output
4. /war-or-game sign-off if metrics improved
5. Record in CALIBRATION_MASTER.md
6. If regression: revert and try different approach
```

**Gate:** All 52w acceptance criteria pass. /war-or-game approved.

## Architectural Decisions (FLAGGED FOR USER REVIEW)

1. **Calibration is NOT autonomous night-shift work.** Phase 2 requires human judgment (War-or-Game sign-off, root cause analysis). Phase 1 (tooling) and Phase 3 (verification) CAN be autonomous. **Phase 2 is DAY SHIFT ONLY.** Night shift should complete Phase 1, then skip to v0.6.2, leaving Phase 2 for day shift. (Cross-plan finding #8.)

2. **One-change-per-run protocol is mandatory** (life lesson). Phase 2 commits are small and frequent. No bundled fixes.

3. **208w full run is expensive** (~5-10 minutes). Reserve for final verification, not iteration. Use 40w for fast iteration.
