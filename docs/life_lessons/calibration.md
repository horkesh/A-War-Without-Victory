### [Calibration] Rule 4 violations are NOT uniformly safe to remove — distinguish wrong-capture from attrition-sink (2026-05-26) — NEW
- **Context**: R29 removed `op:ilijas:krivajevici` from Op Prsten — VRS was CAPTURING it (sim=RS, painted=RBiH, in mismatch list) — result: +9 count (+2.7pp area). R31 removed `op:vogosca:hotonj` from Op Prsten — VRS was FAILING to capture it (sim=RBiH correctly matched, NOT in mismatch list) — result: −17 count (−3.3pp area). Same corpus, same corps. Opposite outcomes. Op Prsten diagnostics confirmed: hotonj was never captured in R29 (op entered recovery with hotonj still as pending objective after 5 other captures). Those brigades spent 4 execution turns in futile combat — which was load-bearing for the HRHB late-war attrition cascade.
- **Wrong approach**: Treating all Rule 4 violations (painted≠faction) as equivalent removal candidates. Rule 4 says "don't add painted-opposite objectives." That logic also implies "remove them." But the attrition effect of TRYING AND FAILING is different from the attrition effect of CAPTURING AND MOVING ON.
- **Right approach**: Before removing any Rule 4 violation, check the oct1995 mismatch list: (1) Is the OSID in the mismatch list (sim=wrong faction)? If YES → VRS is capturing it incorrectly → safe to remove, direct mismatch fix. (2) Is the OSID NOT in the mismatch list (sim=correct faction)? If NOT in mismatch → VRS is failing to capture it → it's an attrition sink → UNSAFE to remove, will free brigades from futile combat → cascade disruption.
- **Do instead**: `node tools/compare_painted_vs_sim.cjs runs/<latest_run> oct1995 | grep <osid>` before removing any objective. If the OSID appears as a mismatch → proceed. If it doesn't appear → it's an attrition-sink, leave it in place.

### [Calibration] Baseline-byte-identical is the proof-of-deadness for cleanup commits (2026-05-29) — NEW
- **Context**: Phase I cleanup arc (Packets I2 / I3a / I4 / I5 / I6) used `tools/scenario_runner/run_baseline_regression.ts` as the definitive proof that each dead-code removal was truly dead. Every cleanup commit landed byte-identical to the prior baseline. Inverse case: an earlier broader I3 cycle (later narrowed to I3a) was rejected during verification when the test surfaced consumers the audit had missed — the regression test was the catch-net that the agent verification step missed.
- **Wrong approach**: Treating `tsc --noEmit` + `vitest run` as sufficient proof that a deletion is safe. Types and unit tests catch obvious removals; they miss runtime consumers that quietly silenced the deleted code from a different call path. The 40w / 188w scenario regression is the consumer integration test for the engine.
- **Right approach**: For any cleanup commit claimed as "pure dead-code removal", verification matrix must include `tools/scenario_runner/run_baseline_regression.ts` PASS byte-identical. If the test reports any artifact-hash drift, the code wasn't dead — restore the deletion and re-investigate. If the test passes byte-identical, the cleanup is provably side-effect-free for the calibration corpus.
- **Do instead**: Add baseline regression to the standard cleanup verification matrix: `tsc --noEmit` + `vitest run <relevant>` + `tools/scenario_runner/run_baseline_regression.ts` byte-identical PASS + `git diff --check` clean. The fourth check is the load-bearing one for deletion safety; the first three are necessary but not sufficient. ### [Calibration] Calibration-overlap deferral is a valid cleanup triage outcome, not a failure mode (2026-05-29) — NEW
- **Context**: Phase I cleanup arc found that ~40-60% of audit-recommended targets land in files concurrently modified on the calibration branch (`claude/calibration-historical-army-arc-2026-05-24`). Each cleanup packet pre-flighted the overlap with `git diff --name-only origin/main...calibration-branch | grep <file>`. Files on overlap were classified DEFERRED-CALIBRATION and skipped. Phase I6 ledger entry shows 5 of 15 entries deferred this way; the deferrals are listed as positive triage outcomes, not as unfinished work.
- **Wrong approach**: Pushing cleanups onto files the calibration branch is editing — produces merge-conflict surface area at the worst possible moment (calibration is the most baseline-sensitive lane in the repo). Or worse: deciding the calibration overlap is "probably fine" without grep verification and committing speculatively.
- **Right approach**: Every cleanup packet starts with the pre-flight grep. Files that overlap are deferred until the calibration branch lands. The ledger entry counts and explicitly names them. "Defer-until-merge" is a positive disposition that prevents real harm; the cleanup will resume on the post-merge tree.
- **Do instead**: As the first step of any cleanup packet, run `git diff --name-only origin/main...claude/calibration-historical-army-arc-2026-05-24` (or whichever calibration branch is currently active) and grep the candidate files. Classify each: NOT-ON-OVERLAP (safe to land), ON-OVERLAP (defer to post-merge). Track the deferred set in the ledger entry as a positive count; it's a queue for the next packet round, not a failure metric.

### [Operations] `planning_duration` and `preparation_max_turns` are parallel timers — the op's declared window doesn't constrain the commander's anti-paralysis (2026-04-02) — NEW
- **Context**: Op Teočak had `planning_duration: 7` but still fired at week 18 (3 turns after injection). `tickPreparation()` sets `preparation_max_turns = getPreparationMaxTurns(aggressiveness)` = `max(2, 8-aggressiveness)`. With aggressiveness=5, that's 3 turns. After 3 preparation turns, the anti-paralysis block auto-sets `preparation_sub_phase = 'ready'`, which triggers execution via `preparationReady` in `sector_offensive.ts:1076` — completely bypassing the `elapsed > planDuration` gate.
- **Wrong approach**: Assuming `planning_duration` on the op definition constrains how long the preparation state machine runs. It doesn't. These are two independent timers operating in parallel layers.
- **Right approach**: At `tickPreparation()` initialization, set `preparation_max_turns = max(aggressivenessMaxTurns, op.planning_duration ?? 0)`. The op's declared planning window becomes a minimum floor that the commander cannot override.
- **Do instead**: Any time an op definition sets `planning_duration`, verify that `preparation_max_turns` initialization respects it. grep `tickPreparation` init block: if it reads `getPreparationMaxTurns(aggressiveness)` without consulting `op.planning_duration`, the declared window is unenforceable.

### [Calibration] Expert hypotheses on regression causes need mechanistic verification before acting (2026-04-01) — NEW
- **Context**: brcko anchor re-failed in n1282 after the `MIN_BRIGADES_FOR_PLAN` depletion fix. The leading hypothesis was "Fix 1 allows thin RS ops to drain Brčko corridor garrison." This was plausible but mechanistically wrong: garrison-locked brigades cannot reach surplus_pool (verified by the garrison floor safety net being dead code). - **Wrong approach**: Designing a fix (must-hold system, corridor garrison multiplier) based on a hypothesis that hasn't been verified against the code. A plausible narrative about cause-and-effect is not the same as confirmed causation.
- **Right approach**: Before acting on a regression hypothesis, trace the mechanism in code. Check: (1) Can garrison-locked brigades actually reach the pool the hypothesis assumes they're drawn from? ### [Calibration] Fix the symptom in ALL callers — AND verify your fix is actually on the code path (2026-03-31)
- **Context**: n1218 fixed `emit.ts` to filter `op.phase !== 'recovery'`. n1225 then fixed `hasAvailableSlot()` in `corps_operation_helpers.ts` — but `commander/emit.ts` never calls `hasAvailableSlot()`; it has its own inline slot guard. The n1225 fix was byte-for-byte inert (identical hash to n1224). 7 calibration runs and ~6 hours spent on wrong diagnoses.
- **Wrong approach**: (1) Fixing a utility function without verifying the code path you care about calls it. (2) Trusting agent code-path analysis as "confirmed root cause" without runtime validation. Both failures occurred here.
- **Right approach**: When fixing any gate condition: (1) grep for all callers of the function, (2) trace the ACTUAL execution path for the failing case (commander ops) and confirm it passes through the function you changed, (3) require a falsifiable prediction ("field X changes from Y to Z") before declaring a fix validated.
- **Do instead**: After applying any fix, check `final_state_hash`. If identical to the previous run, the fix was inert — do not proceed, investigate why the code path wasn't reached.

### [Calibration] When a threshold system isn't biting, check the numerator accounting before tuning the threshold (2026-03-25) — NEW

### [Calibration] Garrison multiplier for must_hold zones can free adjacent brigades toward unintended targets (2026-04-02) — NEW
- **Context**: n1302 showed possible DRINA regression (86.6% vs ~88% at n1289). The must_hold system introduced 1.5× garrison budget for Brcko/Doboj corridors. When a corridor gets a larger garrison budget, the brigades explicitly assigned to corridor defense are locked in. But brigades that were PREVIOUSLY contributing to those corridors as "general pool" may now be freed — because the system considers the corridor "covered" by the multiplied garrison. Those freed brigades drift toward whatever the corps commander selects next, which can include eastern OSIDs in the Drina sector.
- **Wrong approach**: Treating must_hold garrison increases as purely additive and isolated. The multiplier doesn't just lock more brigades in — it changes the whole corps' surplus calculation, potentially freeing brigades that were previously allocated to neighboring fronts.
- **Right approach**: After any garrison multiplier change (must_hold, corridor width, zone priority), check what the ADJACENT corps zone does with freed capacity. - **Do instead**: When adding or adjusting `must_hold` garrison multipliers, include in the validation: (1) count brigades assigned to the protected zone (should increase), (2) count brigades at other fronts for the same corps (should stay stable), (3) check anchors in the ADJACENT zone.
