### [Events] Engine has two write channels for event effects — pick the right one (2026-05-28) — NEW
- **Context**: When authoring event cost-floor effects (`response_options[].effects[]` or `dimension_shifts[]`), the engine routes to two different dispatchers based on which JSON path the entry sits under. `dimension_shifts[].dimension` requires a typed `DimensionId` (6 names only: `military_credibility`, `territorial_legitimacy`, `international_standing`, `patron_confidence`, `internal_cohesion`, `negotiating_leverage`); any other name silently no-ops at runtime. `effects[].kind` requires an `EffectKind` from `EFFECT_KIND_ORDER` (`recruitment_modifier`, `equipment_quality_modifier`, `morale_change`, `patron_pressure`, `alliance_change`, etc.); placing a DimensionId here silently no-ops. The two vocabularies are disjoint.
- **Wrong approach**: Authoring `effects[].kind = "international_standing"` (intent: dimension shift) or `dimension_shifts[].dimension = "patron_pressure"` (intent: pressure effect). Both pass JSON validation. Both silently write nothing at runtime. The cost-floor topology appears in JSON but produces no in-sim signal — counterfactual options become trivially dominant because their punitive cost was authored to a dead channel.
- **Right approach**: Before authoring, decide whether the effect is (a) a per-faction dimension state shift (→ `dimension_shifts[].dimension` with a `DimensionId`) or (b) a typed engine effect with its own consumer (→ `effects[].kind` with an `EffectKind`). Substitute worksheet-language names through `memory/engine_dimension_vocabulary.md` before writing. Trust the loader: as of Packet 44 (2026-05-28), `validateDimensionShiftVocabulary` (`event_loader.ts:939`) + `validateEffectKindVocabulary` (`event_loader.ts:1003`) fail catalog load on any wrong-channel name.
- **Historical cost**: Pre-Packet-44 audit found 11 DEAD writes across 6 packets (4, 9, 17, 19, 23, 38). Packet 38 R12 RS autonomy's entire `patron_pressure` axis was silenced — the counterfactual auto-dominated because its punitive cost-floor was authored to `dimension_shifts[].dimension = "patron_pressure"` (wrong channel; `patron_pressure` is an EffectKind, not a DimensionId). Remediation (Packet 43) re-authored 10 entries to the correct channel; 1 unregistered name (`enclave_resilience`) was removed entirely.
- **Detection signature**: When a worksheet-named delta produces no behavioral effect (zero `formation_delta.json` drift, no AAR change, no anchor movement) AND the multiplier magnitude is large enough that rounding can't explain it, suspect channel confusion first, before suspecting consumer absence. See `memory/engine_dimension_vocabulary.md` for the canonical map.
- **Do instead**: When you add a new `dimension_shifts[]` or `effects[]` row, verify the name is in the correct vocabulary by typed grep: dimensions in `DimensionId` union, effects in `EFFECT_KIND_ORDER`. Loader will catch you, but a 5-second check saves a calibration-run round-trip. Never put `recruitment_modifier` / `equipment_quality_modifier` / `morale_change` / `patron_pressure` / `alliance_change` under `dimension_shifts[].dimension`; never put `military_credibility` / `territorial_legitimacy` / `international_standing` / `patron_confidence` / `internal_cohesion` / `negotiating_leverage` under `effects[].kind`.

### [Events] MAX_EVENTS_PER_TURN=3 creates fragile event chains — pipeline changes cascade into missing events (2026-03-24) — NEW
- **Context**: v0.6.5 added `offensive-paramilitary-detect` pipeline step. This changed early-war state enough that at w5, `jna_withdrawal_1992` got crowded out by 4+ eligible events (barracks events + others). The `jna_withdrawn` flag never fires, breaking the intended cascade to `drina_cleansing`, `operation_corridor`, and `srebrenica_enclave` flag gates.
- **Wrong approach**: Adding a pipeline step and only checking calibration % — not diffing the event firing list. The event dropout was caught by the event_timing test, not by manual review.
- **Right approach**: Before adding any pipeline step that runs in weeks 0-12, run a 40w scenario and diff the event firing list against baseline. If an event drops out, investigate whether its flag is consumed downstream.
- **Do instead**: After any sim-affecting change, run `node -e "... baseline.events_fired.map(e => e.id).sort()"` and compare to the new run. Missing events = broken flag cascade.
