# RS ahistorical presidential playthrough — full 188-week campaign

**Run date**: 2026-08-05. **Status**: investigation only, no engine/UI code changed as a result of this run (the earlier same-day `VerdictScreen`/`WrappedOverlay` fix was a separate, already-shipped piece of work). **Purpose**: at the owner's request — play a full campaign as RS through the real Electron desktop app, choosing the most ahistorical/counterfactual option at every decision point and firing every presidential lever as constantly as possible, to measure how much the game railroads the player back toward the historical outcome.

**Revision note**: this document was corrected in place on 2026-08-05 after a 12-specialist Pyrrhic panel review found four factual errors in the original draft (detailed in the sections below where they occurred, not just banner-noted). A first correction pass left a stale duplicate block and an unresolved self-contradiction on `vrs_main_staff` — caught by Retrospective Analyst reading this file fresh — and this is the follow-up cleanup. Full panel findings, attributions, and prioritized recommendations: `docs/40_reports/20260805_RS_PLAYTHROUGH_PYRRHIC_PANEL_SYNTHESIS.md`. Read that document for the bold recommendations; this one is the primary-source evidence record.

## Method

A Playwright script (`tools/ai_play/electron_playthrough_rs_ahistorical.mjs`, not wired into any npm script — ad hoc) launched the actual Electron app (`electron .`) and drove it through `window.awwv.*`, the exact `contextBridge` surface the real UI buttons call (`src/desktop/preload.cjs` → `src/desktop/electron-main.cjs` `ipcMain` handlers). Every mutation — event decisions, presidential levers, turn advance — went through the same IPC path and the same engine a human player uses. This is not the headless `scenario_runner` (which forces `headless_scenario_auto_control` and bot-resolves everything); it is the desktop player-decision seam, run unattended. Scenario Harness Engineer's panel review notes a stronger, determinism-proven alternative already existed for part of this job (`tools/ai_play/president_playthrough.ts`) and should be the base for any repeat of this exercise — see the synthesis doc.

**Per turn, the script:**
1. Resolved every pending decision for RS across all decision families (`event_decision`, `peace_plan`, `paramilitary_request`, `convoy_decision`, `dayton_negotiation` — the full set in `src/state/player_decision_manifest.ts`), always picking the option explicitly marked `counterfactual`, else any option that wasn't the `historical_default`.
2. Fired all three leadership gestures when available: Front Visit, Address the Nation, Decorate a Unit.
3. Attempted REPLACE-CO, STOP-OP, FORCE-LAUNCH (on any pending proposal), REQUEST-OP, ELITE-DEPLOY, and Local Support for every RS corps/request, every turn, gated only by whatever the engine itself allows (command authority, cooldowns, eligibility).
4. For REQUEST-OP specifically: targeted enemy-held OSIDs, preferring ones matching Sarajevo/Tuzla/Goražde/Bihać/Srebrenica/Žepa/Mostar/Brčko — i.e., places RS never held historically — to directly test whether the president can even *order* an ahistorical offensive.
5. Advanced the turn, retrying through any blocking decision.

**Two explicit doctrine choices, stated up front so the results aren't misread as "the engine forced this":**
- **Peace plans**: always rejected, to keep the war running its full ahistorical course rather than truncating early.
- **Paramilitary integration requests**: always denied — a deliberate ethical choice on my part, not something the engine required. **Correction**: the original draft speculated this choice was "plausibly connected" to Srebrenica not falling. It wasn't — see the Srebrenica bullet below.

**Known gap, confirmed by Gameplay Programmer's panel review**: the script never accepted RS's pre-planned-operation authorization reviews (it pattern-matched the wrong proposal prefix — see "The `operations_launched: 0` finding" below) and never raised `autonomy_level` above its default of 0, so RS's own corps AI never got to propose operations either. This run measures RS's *political* agency accurately; it does not measure RS's *offensive military* agency, because that gate was never opened. A repeat run needs to fix both.

**One honest methodology gap**: the script drove state via IPC only; it never clicked the real "New Campaign" / "Continue" UI buttons, so the main window's on-screen view stayed on the main menu for the whole automated run (confirmed separately — see "Screenshots didn't show live gameplay" below). This means the mid-campaign screenshots are not useful UI evidence; the real UI evidence in this report comes from a dedicated recon pass (tactical map + settlement panel) and a separate verification pass (the "Continue" button).

## Headline answer: how much does the game railroad the player?

**On the political/decision axis: not much. On the aggregate territorial axis: quite a bit, converging back toward history by the end anyway.**

The engine's own endgame `historical_comparison` block (computed independently of anything I wrote) is the cleanest evidence:

```
"divergence_notes": [
  "Federation controlled 54.1% territory vs historical 51%",
  "RS controlled 45.9% territory vs historical 49%",
  "Srebrenica enclave survived",
  "Total military casualties were 95% of historical levels",
  "War lasted 6 weeks longer than the historical 182 weeks"
]
```

- **13 major historically-loaded decisions were faced; all 13 could be answered counterfactually, and the engine accepted every single one** — overriding the Bosnian Serb Assembly's rejection of Vance-Owen (turn 56), accepting Owen-Stoltenberg with modifications against Belgrade's wishes (turn 75), defying a direct Belgrade directive (turn 76), pursuing autonomy-within-BiH instead of independence (turn 89), accepting the Contact Group 51/49 plan (turn 118), going defiant against a Belgrade embargo (turn 121), maintaining the UN hostages in May 1995 instead of releasing them (turn 160), **removing Mladić** when Karadžić moved against him (turn 174, historical default was `back_down`), defying the US-Belgrade channel (turn 176), and absorbing NATO airstrikes rather than withdrawing heavy weapons (turn 178). None of these were blocked, watered down, or silently reverted. The president can genuinely steer RS's politics away from history. **Historian's panel review, important caveat**: two of these (removing Mladić; accepting Contact Group 51/49) were accepted too cheaply relative to the historical record — Karadžić tried removing Mladić for real on 4 Aug 1995 and was forced to reverse it 7 days later after VRS Main Staff officers sided with Mladić against Pale (BB1 p.75, p.434, p.463); Contact Group acceptance was blocked in reality by RS's own 27–28 Aug 1994 referendum against Belgrade's wishes (BB1 pp.59–61). The engine currently has no RS-internal institutional veto layer (Main Staff loyalty, Assembly/plebiscite) that would contest either. Two others (defying Belgrade broadly; absorbing airstrikes) are judged historically sound or partially sound by Historian — see the synthesis doc for the full breakdown.
- **REQUEST-OP toward historically-untaken targets was never rejected outright.** 15 directives were staged successfully toward Goražde, Srebrenica-area OSIDs, Tuzla (including Tuzla city itself, `op:tuzla:tuzla_2`), Mostar East, and Brčko-area OSIDs. The engine didn't say "no, RS can't attack there." But **none of these translated into a lasting change of control**. The engine computes and stores exactly why each one failed (`cmd.op_directive_rejection = { target_osid, reason, turn }`, `war_phases.ts:853-855`) — but per Architect, UI/UX Developer, Game Designer, and Gameplay Programmer's panel review (four independent confirmations), **that field has zero readers anywhere in `src/ui/**` or the desktop adapter**. It is computed, persisted, projected to the client, and never shown to anyone. So the soft railroad isn't at the "can you order it" layer, it's at the "can you actually win it, and are you ever told why not" layer — the president has the authority, spends real Command Authority on it, and the explanation the engine already wrote down is thrown away before it reaches the screen.
- **Aggregate territory still converges close to history**: RS 45.9% vs historical 49% (only 3.1 points low), Federation 54.1% vs historical 51%. Given every major political lever was pulled toward maximal defiance and CA was poured into corps-level intervention nonstop, ending within ~3 points of the historical split is a real, measurable "gravity" back toward the historical outcome — but it is not a hard wall. It moved, just not far. **Historian's panel review**: treat this specific number with caution rather than as clean railroading evidence — 45.9% sits close to the actual late-1995 battlefield line, while the historical 49% was a *negotiated* Dayton restoration, not a military result, and this run's own Dayton resolution was accidentally malformed (see below). The convergence may be measuring "the military layer is roughly right" more than "politics can't move territory."
- **Casualties were 95% of the historical count** — essentially the same scale of war, despite completely different political choices. Historian judges this independently plausible: BiH war attrition was geography- and manpower-driven, and high-political counterfactuals wouldn't be expected to move it much.
- **Dayton arrived 6 weeks late** (week 188 vs historical week 182) rather than never, or wildly early/late.
- **Srebrenica did not fall, and no genocide occurred** (`milestone_comparison` explicitly records `srebrenica_genocide_1995` as `status: "absent"`) — real, and the strongest positive evidence in the whole run that atrocity in this game is genuinely contingent rather than scripted, which is exactly what the project's own sensitive-history design gate requires. **Correction, confirmed independently by both Historian and Canon Compliance Reviewer's panel review**: the original draft claimed this was "plausibly connected" to denying paramilitary requests. That's wrong — `srebrenica_falls_1995`'s actual trigger (`data/scenarios/events/war_1995.json`) has no paramilitary predicate anywhere in it; it fires purely on `turn_min 160, turn_max 185, phase war, srebrenica_enclave_formed == true, srebrenica_demilitarized == true`. Denying paramilitary requests could not mechanically have prevented the fall. The non-fall is real and is the canon-correct *kind* of outcome; this report's specific causal story for *why* it happened is fabricated. The real open question — which of the two gating flags never got set, and why — is unresolved and belongs to a follow-up investigation, not a repeat of the paramilitary-denial hypothesis (Canon Compliance Reviewer: any repeat run should be explicitly framed as falsifying that hypothesis, not confirming it).

### The `operations_launched: 0` finding — real number, wrong original framing

`meta.endgame_snapshot.verdict.faction_verdicts.RS.capital_breakdown` — the game's own scoring, not anything I computed — says, for the **entire 188-week war**:

```json
{
  "operations_launched": 0,
  "operations_successful": 0,
  "combat_effective_brigades": 11,
  "military_casualties_inflicted": 93411,
  "military_casualties_taken": 209266,
  "territory_controlled_pct": 45.9393009642101,
  "enclaves_held": [],
  "war_crimes_events": 4
}
```

HRHB's own equivalent block, for comparison, shows `operations_launched: 2, operations_successful: 1` — not high either, but non-zero. RS shows **zero, all game**.

**Verification note** (the owner correctly pushed back on this as implausible, so it was checked directly rather than taken on faith): `compute_capital.ts`'s `computeMilitaryData()` computes `operations_launched` as `state.operation_history.filter(aar => aar.faction === faction).length` — a plain count of completed-operation AAR records, run server-side against the real (unredacted) state, and frozen into `meta.endgame_snapshot` once at game-over. This is a *different* code path from what `window.awwv.getCurrentGameState()` returns to a running client (that goes through `projectPlayerVisibleStateJson`, which filters `operation_history` down to the player's own faction's rows only — fog of war). Re-reading `final_state.json` after the run, its top-level `operation_history` array is empty for every faction — at first this looked like a contradiction (HRHB's frozen "2" should have produced 2 rows somewhere), but it isn't one: an RS player is *structurally never shown* HRHB's operation rows regardless of how many exist. The frozen verdict number itself is unaffected by that projection, so **RS `operations_launched: 0` stands** as a real, server-side-computed figure, not a reading error.

**Correction (the original draft called this "the sharpest railroading finding in the whole run" and asked the panel to investigate whether it was an engine defect). It is not an engine defect, and it is not evidence of railroading.** Gameplay Programmer's panel review traced the exact mechanism: `deferUnauthorizedHistoricalOperationsForPlayer` (`historical_operation_authorization.ts:124-163`, called from `desktop_sim.ts:291` at campaign start) strips RS's entire historical offensive slate — Koridor, Prsten, Drina, Prijedor, Višegrad, Zvezda 94, Trnovo, Pračha River — out of `active_operations` and parks it as unresolved `pending_proposal_reviews` entries prefixed `HISTORICAL_OP:`. My script only ever pattern-matched proposals prefixed `APPROVE_OP:`, so it never accepted a single one of those reviews, for 188 consecutive turns — and `inject-player-pre-planned-operations` (`war_phases.ts:1794-1809`) only re-injects a player's pre-planned ops once at least one such review is accepted. Separately, RS's `autonomy_level` defaults to 0 and the script never raised it; `selectBotBrigadeOrderFactions` (`war_phases.ts:923-934`) excludes the player faction from bot-driven corps order generation unless `autonomy_level >= 1`, so RS's own commander AI never proposed an operation either. Both routes to a `CorpsOperation` were closed the entire game, by the script, not the engine.

Formation Expert's panel review adds a second confound now resolved: `combat_effective_brigades: 11` looked like possible attrition damage from the constant REPLACE-CO churn, but a check against the untouched 188w calibration baseline shows RS at 7/53 combat-effective *there too* — this run's interventionist president actually did *better* than the passive bot baseline on that metric, which rules out the officer-churn confound entirely. The real driver, per Formation Expert, is an unbounded morale asymmetry in `morale_drift.ts` (RS's victory/defeat multipliers are less generous than RBiH's, with no ceiling on how far the gap compounds over 188 weeks) that also plausibly explains a previously-unsolved, already-documented finding from a prior session (RS brigade-destruction asymmetry). Full detail in the synthesis doc.

The genuinely interesting, still-standing finding underneath the correction: **a president at autonomy 0 who never finds the historical-operation-authorization surface plays an entire war in which their own army never launches a single offensive**, and RS still ended up holding 45.9% of the country purely through defensive combat and other factions' activity. That is a real and significant player-experience finding — a silent, unexplained gate that a real (non-scripted) player could plausibly also never find — it just isn't the railroading finding it was originally framed as.

`RS`'s overall endgame grade: `outcome_class: "pyrrhic_success"`, letter grade **C** ("45–49% territory, some international concessions — capped by war cost"). Every soft-power dimension graded **F** except `territorial_legitimacy` (**D**): military_credibility F (9.7/100), international_standing F (0/100), patron_confidence F (0/100), internal_cohesion F (0/100), negotiating_leverage F (0/100). Full `milestone_comparison`: Srebrenica Genocide `status: "absent"`; Dayton Accords `status: "late"` (player week 188 vs historical week 182, delta +6 weeks). Canon Compliance Reviewer's panel review traced the grade C to a specific, functioning-as-designed mechanism (`COST_GRADE_CAPS` in `scoring.ts`, capping the grade by a war-cost index that RS's 209k casualties / 188-week duration / 4 war-crimes events all saturate) that `VICTORY_AND_PYRRHIC_SCORING.md` §3.2 currently doesn't document — a canon-doc gap, not a scoring bug.

### `vrs_main_staff` and REPLACE-CO eligibility

VRS Main Staff is not a field corps — it is the supreme command entity (Mladić's own seat), and the owner corrected an earlier draft of this report that had listed its lack of a "current CO" as a possible data gap. "No current CO" there is expected. My automation's REPLACE-CO loop naively iterated every key in `state.military.corps_command`, which conflates true field corps with Main Staff, and offered REPLACE-CO against Main Staff 123 times across the campaign, all correctly rejected (no CA was ever charged for these — `co_replacement.cjs` debits CA only after every eligibility check passes, so the 123 failed attempts cost the run nothing).

**The panel's correction to the correction**: multiple independent reviews (Formation Expert, Gameplay Programmer, Systems Programmer, Scenario Harness Engineer) found that the "field corps vs. supreme command" distinction this raised as an open question is **not actually missing from the codebase** — it already exists in at least three places: `kind: "army_hq"` in `data/source/oob_corps.json`, `EXEMPT_CORPS_IDS`/`isSectorAssignmentExemptCorpsId` in `src/sim/combat/corps_front_sectors_constants.ts`, and `main_staff_formation_id` in `src/sim/combat/army_co_lifecycle.ts`. `co_replacement.cjs` (and the other corps-scoped lever handlers) simply never read any of them. The fix is a filter using data that already exists, not a new type or a missing eligibility model.

| Local Support | 189 | 189 | 100% success, every turn — **correction below: this is not a free/unlimited lever** |
| **CA-insufficient blocks (all levers combined)** | **270** | — | Command Authority is the dominant real constraint on "constant" presidential activity |

Practical read: **Command Authority, not engine permission, is what actually limits a maximally interventionist president.** Every lever that costs CA (25 for Replace-CO/Stop-Op/Request-Op/Elite-Deploy, 10 for the three leadership gestures) hit real scarcity once the initial reserve was spent — by turn ~25 in an early smoke test, over half of all attempted lever uses were CA-blocked. Game Designer's panel review confirms this is the CA economy working exactly as designed (post-PR #474 "Option B political income": ~29 override acts of lifetime budget for a whole campaign, so a script firing 1,251 corps-lever attempts *should* be blocked most of the time — "that number is the system succeeding," in Game Designer's words).

**Correction on Local Support**: the original draft called this "free (no CA cost, no cooldown found)" and treated 189/189 as evidence of an unlimited lever. Game Designer's panel review checked the actual code: `municipality_support_orders` is a **single slot per faction that expires the turn it's staged** (`src/sim/combat/municipality_support.ts:32` requires `staged_turn === currentTurn`). The 189 "successes" are 189 overwrites of one weekly slot, not 189 accumulating buffs — it's scarce by exclusivity, not by price. This maps to a real, deliberate two-tier lever taxonomy in the Game Bible (CA prices *override of the command chain*; Local Support is administrative prerogative that overrides nobody) rather than an oversight. The one real, still-standing defect Game Designer flags: because it's free and always available, there's currently never a reason *not* to fire it, making it a mandatory weekly click rather than a real decision.

## Bugs, inconsistencies, and things worth engine-team attention

1. **`pending_dayton` is never cleared after the game reaches `game_over` — root cause now fully identified.** At the endgame transition, the final saved state has `meta.game_over: true`, a fully computed `meta.endgame_snapshot.verdict.dayton_result`, *and* `military.negotiation.pending_dayton` still present. Because `listBlockingPlayerDecisions` treats a present `pending_dayton` as a hard block, `advance-turn` kept returning `pending_required_decisions` for the rest of the run — my script called `resolveDayton` 62 times over about 90 seconds before giving up and reading state directly, at which point the game had already actually concluded. An earlier draft of this report guessed the cause was a `meta.phase !== 'war'` guard; that was verified wrong (`meta.phase` stays `"war"` even at game-over) and the real cause needed to be found by reading code, not guessing. **Four independent panel reviews (Technical Architect, Systems Programmer, Gameplay Programmer, Determinism Auditor) converged on the same answer**: the only code that ever deletes `pending_dayton` is `resolvePendingDaytonCloseOut` (`src/sim/negotiation/dayton_negotiation.ts:216-231`), gated on `state.meta.dayton_close_out !== true` (line 217) — a flag that only `scenario_runner.ts` (the **headless** runner) ever sets, at `scenario_runner.ts:1593-1594`, with its sole call site at `scenario_runner.ts:2880`. The real player path (`resolveDaytonNegotiation`, called from `electron-main.cjs:3272-3290`) writes `dayton_result`, sets `game_over`, freezes the endgame snapshot — and **never deletes `pending_dayton` itself**. Request and receipt are written by two different owners with nothing enforcing they travel together. Technical Architect's addition: because `advance-turn` checks the blocking-decision gate *before* running the turn pipeline, the dangling packet permanently blocks the only path through which any pipeline-based cleanup could ever reach it — a self-sealing deadlock, not just a missed cleanup step. Determinism Auditor's addition: this is player-reachable too, not automation-only — the real Dayton modal's "Decline Talks" only clears the client's local copy, never server state. Same *shape* of issue as this session's earlier `VerdictScreen`/`WrappedOverlay` bug (something not cleaned up at the exact game-over boundary) — QA Engineer independently flagged this as the second same-shape bug in one day and recommends a general terminal-state invariant rather than a family-specific patch. Full recommended fix in the synthesis doc.

2. **RS never had a live operation to STOP, FORCE-LAUNCH into, or fill an ELITE-DEPLOY/reserve request for, after the opening turns** — all four presidential-action tallies read 0/0. See "operations_launched: 0" above for the full, now-corrected explanation (a script bug, not RS-specific engine unreachability) — Formation Expert additionally confirmed RS's turn-0 startup snapshot genuinely does carry pre-planned operations for 6 of 8 corps, which reconciles with the deferral mechanism: those ops existed and were immediately parked before this script's first read.

3. **Screenshots taken during the automated turn loop are not real UI evidence** — every one of them (turn 1 through turn 181, plus the final-state screenshot) is byte-identical, because the main window stayed on the Main Menu the whole time. This is *not* an engine bug: I verified separately that the real "Continue" button, clicked for real, correctly drops straight into the live Presidential Desk view with the correct date, correct pending-decision count in the status bar ("REQUIRED 2 · REVIEW BEFORE ADVANCE 7 · PENDING 7"), and full navigation (President's Desk / Command Surface / Diplomacy / Intelligence / Army HQ / Chronicle / Faction / War Map / Advance). It's an artifact of driving state purely through IPC without ever clicking a UI navigation button — worth knowing before trusting any future headless-UI screenshot harness that doesn't also drive real clicks.

4. **The settlement info panel's bottom section is "Local Support"** (direct answer to the question asked mid-run): a `weapons_shipment` / `staff_priority` / `croatian_support_package` order, faction-restricted — RS is server-side rejected (`"Invalid municipality support type for RS: weapons_shipment"` / `"...croatian_support_package"`) for the other two factions' types, confirmed by the actual IPC handler, not just hidden in the UI. See the correction above: it's a single expiring weekly slot, not an unlimited free lever. Screenshot evidence shared in this session's chat.

5. **Cosmetic-only console noise**: `Autofill.enable` / `Autofill.setAddresses` DevTools protocol errors fire on every launch. These are a well-known Electron/Chromium DevTools artifact (the app doesn't implement the Autofill CDP domain) and are unrelated to the game; zero `pageerror` events were recorded across the entire 188-turn run, and no other console errors of any kind fired.

6. **New, unrelated finding from panel review, not from the playthrough itself**: Systems Programmer found the Electron IPC layer has no mutation serialization — every mutating `ipcMain.handle` does read-modify-write against one shared JSON string with no locking, and Electron does not serialize concurrent `invoke` calls. Two overlapping presidential actions can both pass their own "not already pending" guard, both compute a valid mutation, and the later write silently overwrites the earlier one — losing an order and its CA debit with no error to either caller. This is a live correctness bug for real rapid double-clicks, independent of anything this run's automation did. Full detail and recommended fix (a promise-chained mutex) in the synthesis doc.

## Data notes / caveats

- The 3.1-point RS territorial shortfall vs. history remains **confounded** and this run cannot cleanly attribute it between the counterfactual political choices, Command Authority being spent on constant lever-spam rather than left for the engine's own corps AI, and the now-known-broken offensive-authorization gate (see above). A repeat run with the authorization gate opened and `autonomy_level` raised is needed before drawing a real conclusion here.
- **Dayton resolution — retracted as engine evidence, not just caveated.** The original draft described resolving Dayton by "echoing the pending proposal object back," producing `territorial_packages_accepted: []` and a `peace_dysfunction_index` of 84.4, and called this "a blunt default" consistent with "maximally obstinate RS." Panel review (Determinism Auditor, mechanism; Scenario Harness Engineer, verdict) found this framing was too soft: the echoed payload's missing fields (`territorial_demands`, `territorial_concessions`) silently fell back via `|| []` coercion (`electron-main.cjs:3281-3283`) to `buildHistoricalDefaultDaytonProposal()` (`dayton_negotiation.ts:187`) — meaning the run actually signed a well-defined **historical-default** settlement, not a deliberate rejection of every package. The resulting numbers are neither random garbage nor a genuine "maximal RS defiance at the table" data point; they're the correct, deterministic output for a specific default input the script didn't intend to send. **Treat every number under this bullet as invalid evidence about the engine or about RS's negotiating posture.** A real test of Dayton behavior needs an actual accept/reject response builder, not an echoed pending-state object.
- Full raw evidence: `log.jsonl` (2,323 entries), `anomalies.jsonl` (132 entries), `final_state.json`, and screenshots are in the session scratchpad (not committed to the repo — ephemeral investigation output, available on request). Scenario Harness Engineer's panel review flags this as a real loss-risk: none of this evidence is committed or reproducible by anyone else today.
